# Warp Simulator Phase 0：架构与概率模型调查

调查日期：2026-10-15（Asia/Shanghai）。本报告只描述下表固定来源的调查结果与后续建议，不代表已经实施迁移，也不覆盖工具站的现行规范。

## 1. Executive Summary

**建议重写概率与身份边界，保留旧项目的功能组织、会话分离思路和有价值的测试场景。现有本地资料不足以建立“官方精确算法”的完整 Canonical Truth。**

- 原始配置可以确认跃迁类型、部分 UP 配置值、常驻 300 抽自选条目、星缘相邀的七名选择及 Fate 联动保底独立范围；不能从这些配置直接读出完整的五星／四星基础概率、Soft Pity 曲线或服务器抽样算法。
- 旧引擎在角色第 74 抽仍使用 0.6%，第 75 抽跳至 12.6%；光锥第 66 抽仍使用 0.8%，第 67 抽跳至 14.8%。这是可复现的代码行为，与项目宣称的起点不一致，但本轮没有足够本地证据宣布另一条曲线就是官方算法。
- 已确认的工程缺陷包括：对象引用导致自定义 UP 误判、浅层导入校验接受无效物品及重复身份、无效池可以产生 `undefined` 且已修改保底状态。应优先解决身份、验证和原子提交，再讨论概率校准。
- 当期 UP 再次出现在回退候选中，不能一概判为 Bug：本地文本明确存在星缘选择包含当期 UP 的情形。旧实现无条件追加 UP、重复身份及最终命中率与分支概率的混用，需要分别审查。
- 当前 Vue 旧项目已经实现独立／共享两种会话；模式切换保持两套状态，共享重置明确同时清空角色和光锥。十连与十次单抽等价，不能把这些实现强行列为错误。
- 推荐分离 Probability Model、Pool Resolver、Gacha Engine、Session State，并按模型版本记录证据。普通角色、普通光锥、联动角色、联动光锥及自定义沙盒不应只依靠两类全局状态区分。

旧项目现有五个测试文件、32 个用例全部通过。内存探针及两组百万抽统计也已执行；它们验证实现与所选旧模型的一致性，**不证明模型等于游戏算法**。本轮只新增本报告及其目录，不实施引擎、数据或 UI 迁移。

### 3.2 Soft／Hard Pity 的实际公式

令 `n = nonGoldGachaCount + 1`，表示自上次五星后即将进行的第 n 抽。以下都是 **C 级旧实现公式**，不是经认证的社区或官方模型。

- 角色／常驻：n ≤ 74 时阈值为 0.006；n ≥ 75 时为 `0.006 + (n - 73) × 0.06`。
- 光锥活动：n ≤ 66 时阈值为 0.008；n ≥ 67 时为 `0.008 + (n - 65) × 0.07`。
- 四星：令 `m = nonPurpleGachaCount + 1`；m ≤ 9 时条件阈值为 0.051；m ≥ 10 时为 `0.051 + (m - 8) × 0.5`。

| 即将进行的抽数 | 角色／常驻五星阈值 | 光锥五星阈值      | 四星条件阈值       |
| -------------- | ------------------ | ----------------- | ------------------ |
| 73／74／75     | 0.6%／0.6%／12.6%  | —                 | —                  |
| 65／66／67     | —                  | 0.8%／0.8%／14.8% | —                  |
| 89／90         | 96.6%／102.6%      | —                 | —                  |
| 79／80         | —                  | 98.8%／105.8%     | —                  |
| 8／9／10       | —                  | —                 | 5.1%／5.1%／105.1% |

因为随机整数范围是 0–999，超过 100% 的阈值在旧代码中实际等价于必出。因此有效五星上限为角色／常驻 90、光锥 80；四星或以上最多间隔十抽。没有显式 Hard Pity 分支，不代表旧模型没有有效上限。新模型宜显式处理上限并约束概率在 [0, 1]，不靠数值溢出实现保底。

例如“第 74 抽 6.6%、第 66 抽 7.8%”可以由更早启用同一线性增量得到，但**本轮没有对应社区统计出处或官方精确算法证据，不能把这一候选表达升格为修复真值**。四星第九抽的 55.1% 也只是旧项目宣称的线性意图，不能据 C# 注释认定游戏如此。

### 3.3 四星、五星优先级与状态转移

`doGacha` 首先抽五星；失败后使用另一次 RNG 抽四星。因此在基础区间：

`P(4★) = (1 - P(5★)) × P(4★ | 本抽非五星)`

角色／常驻为 `0.994 × 0.051 = 5.0694%`，光锥为 `0.992 × 0.051 = 5.0592%`。这确认了条件／边际区别；是否违背游戏的基础概率口径仍需规则证据，不能仅从“5.1% 常量”判断已经准确。

五星分支同时把五星和四星计数归零，但不触碰 `missedPurpleEventItem`；四星只重置四星计数并更新四星 UP 保证；三星两个计数加一。已复现四星计数为 9、四星保证为 true 时抽到五星：计数归零，四星保证仍为 true。

这可以满足“十抽内至少一个四星或以上”的弱约束，却不足以确认“五星替代、推迟或重置四星保底”哪种机制符合游戏。后续模型需在五星／四星同时到达保底时给出明确分布与状态转移，不能只测试批次里有高稀有度。

### 3.4 UP 分支、候选重叠与身份

旧内置数据包含：普通五星 14 项（角色 7、光锥 7）、星缘角色 7 项、普通四星 53 项（角色 22、光锥 31）、三星光锥 25 项、全五星扩展 128 项（角色／光锥各 64）、活动配置 28 项（启用 14 项）。所有启用池的三名 UP 四星都存在于普通四星池中。

在未保证、只有一个 UP 五星且不与七项背景候选同名的情况下，旧引擎的最终命中率为：

| 条件于本次稀有度命中且未处于 UP 保证 | 分支率 | 回退候选重叠                 | 最终 UP 物品命中率                |
| ------------------------------------ | ------ | ---------------------------- | --------------------------------- |
| 角色五星                             | 50%    | 回退池八项中有追加的 UP 一项 | `0.5 + 0.5 / 8 = 56.25%`          |
| 光锥五星                             | 75%    | 同上                         | `0.75 + 0.25 / 8 = 78.125%`       |
| 内置角色四星                         | 50%    | 普通四星池 53 项含三项 UP    | `0.5 + 0.5 × 3 / 53 ≈ 52.8302%`   |
| 内置光锥四星                         | 75%    | 同上                         | `0.75 + 0.25 × 3 / 53 ≈ 76.4151%` |

这些不是包含保证周期的长期 UP 比例，更不是每次跃迁的 UP 概率。原始 50／75 字段没有给出完整的分支／最终物品解释，所以本轮把光锥回退包含 UP 列为高价值待核验项，不直接宣布它必须被排除。

星缘文本说“选择七名”和“五星可为当期 UP 或星缘角色”；它不直接说明回退分支抽样范围。旧星缘选择文件仍是七名，追加 UP 后回退数组为八项：**不能把八项回退数组简单说成玩家选择了八名，也不能未经证据把该数组认定为准确**。应独立验证分支语义、重复 ID、权重及重叠后的保证转移。

对象身份问题另有明确证据：自定义 `eventPurple` 由 `toItemData` 重建，而 `standardPurpleItems` 来自初始化加载。相同 Name 的两份对象不相等；探针强制走回退抽中该 UP 四星，结果名称相同但 `isPurpleGuaranteed` 为 true。

同类风险也影响星缘中的五星：星缘 JSON 与 AllGold 主目录分别加载，若当期 UP 已在七名星缘中，两份同名对象可能不同。回退抽中星缘版本时会被记为歪；追加 UP 还会产生重复抽样身份。当前启用内置角色池没有这一同名重叠，不能声称所有内置池正在触发；自定义或后续启用重叠池时需要 ID 级回归测试。

内置四星通过 master lookup 复用普通四星对象，所以回退再次命中 UP 时能按其当前引用语义识别为 UP。这个实现局部是自洽的，不能与自定义引用缺陷混为一谈。

### 3.5 共享、继承、重置与批量抽取

- `loadPityMode` 默认 `individual`；同类型活动池可使用 `sharedAvatarState` 或 `sharedLightConeState`。共享包含计数、五星／四星保证、历史和五星记录，而每个系统保留本池成员。
- `setPityMode` 选择另一套会话，保留两边已有状态，不执行迁移／合并。README 的“独立状态”未完整描述今天的代码，但不能推断代码缺少共享功能。
- 共享模式 `resetActivePity` 同时清空两类活动共享状态；`PullControls.vue` 和 TextMap 的确认文案明确告知这一范围，测试也固定了此行为。它是产品选择，不是无提示的错误重置。
- 常驻、全五星扩展池不参与活动共享。自定义池目前参与对应普通活动共享，这是游戏／沙盒边界风险；目前关闭的 Archer、Saber 等联动条目没有特殊类型与继承分组，不能直接启用后宣称准确。
- 引擎记录 `isMissed` 时使用当次所属池，不在后续切换池时重新分类，避免把先前命中 A 池 UP 的物品在 B 池中改记为歪。但 History 只存 ItemData，没有 Banner ID／模型版本，不足以进行按池审计或可靠导出恢复。
- `pull10` 连续调用十次同一 `doGacha`，随后追加历史。固定随机序列探针确认结果、终态和 RNG 调用次数与十次 `pull` 相同；四星计数保证正常配置下不会出现十个三星，无需额外批次替换。

### 3.6 RNG、物品权重、特殊池与统计

千分位比较是 0.1 个百分点的格点，但旧阈值 6、8、51、500、750 及线性增量均为整数，当前概率不会仅因离散化发生额外舍入误差。`pickRandom` 对数组索引均匀抽样，在 RNG 均匀的前提下符合旧模型。没有证据可以认证常驻角色／光锥分类权重、四星物品权重或潜在防偏机制就是这种均匀分布。

UP 保证时仍先调用 `isEvent`，因为表达式是 `isEvent(...) || isRateUp`。这会消耗一个用不到的随机数，但不降低保证命中率；旧测试明确检查调用数。新实现可以定义更清晰的 RNG 协议，不把这次消耗认作概率 Bug，也不承诺与旧随机轨迹逐抽兼容。

常驻混合角色／光锥但使用角色五星曲线；全五星扩展池只是扩大五星成员，**不是每抽必五星**。它不是原始 GachaType，应该标注为沙盒。旧项目没有新手 50 抽／八折生命周期、常驻 300 抽自选状态或独立联动模型；这些都不能通过替换成员列表自动获得。

`lastGoldPullIndex / goldCount` 可以解释为从零开始的已完成五星间隔均值，排除未完成尾部，不直接判错。`lastGoldPullIndex / rateUpGold` 的含义不够清楚：例如第 10 抽 UP、第 20 抽非 UP，它返回 20，而已完成 UP 周期均值为 10；若定义为累计资源比则又排除了随后非五星尾部。应分别命名与展示，不用“平均 UP 抽数”掩盖不同指标。

`missedGold / goldCount` 包含保证五星，不是非保证 50／50 或 75／25 的失败率。在共享历史中，UP 还可能指不同池抽取时各自的 UP；不能把它展示为“当前角色获取次数”。新版事件需保留抽取前保证状态、分支和当时 UP 判定。

| Probability Model     | ResolvedPool + 保底／保证状态 → 结果类别分布及转移规则                  | 提供模型 ID／Version、适用范围与证据；明确边际或条件概率、Hard Pity、碰撞处理和保证转移。理论分析不依赖 RNG                           |
| Gacha Engine          | 已验证池 + Session State + `Rng.next(): number` → nextState + PullEvent | 纯 TypeScript 抽样与状态转移；RNG 值需有限且在 [0,1)。不导入 Vue、翻译、DOM、FS 或原始 JSON；十连顺序执行同一转移，完整候选成功后提交 |
| Session State／工具层 | 用户动作 + 抽取事件 → 单一已提交会话 + 派生统计／展示                   | 按显式继承组保存计数和保证；保存抽取时物品、Banner、模型身份及保证上下文。选择、弹窗、草稿和计算中间缓存不是第二份业务会话            |

数据流应为：**固定来源 → 显式更新器／人工审阅 → 仓库内规范化快照 → Resolver／模型 → 引擎 → 完整会话提交 → 展示、统计与持久化**。纯引擎只接收规范化后的运行上下文，不解析 raw game JSON。

建议给物品加类型命名空间，如 `avatar:<AvatarID>`、`light-cone:<EquipmentID>`；Banner 使用来源 GachaID，而一次复刻与同角色的首次池保留不同 Banner 身份。保底分组独立于 Banner ID 与 UI GroupID；Fate 角色和光锥需独立于普通类型，自定义沙盒使用自己的会话域。普通活动的具体继承规则仍须补证后落入 profile。

历史应记录抽取时“是否处于保证”“是否命中 UP 分支”“最终是否为当期 UP”，三者不可混为一个 isMissed。统计按事件上下文计算，切池或切语言不重新解释旧记录。星缘选择变化只影响后续解析，不改写先前事件；其对保证状态的影响需单独核验。

### 5.3 从原始数据建立稳定 ID 卡池

已交叉检查 290 条活动／联动 GachaBasicInfo 主 UP PrefabPath：对应 ID 均能在 AvatarConfig + AvatarConfigLD 或 EquipmentConfig 找到五星记录。其中普通角色／光锥各有 54 个不同主 UP 实体，联动各 4 个。联动的四个角色不在普通 AvatarConfig，不能因普通表查不到就创建虚构物品。

路径中的 `AvatarGacha_<ID>`／`LightConeGacha_<ID>` 是**经该快照全量验证的关联线索**，不是正式物品成员字段。若后续更新器使用它，应固定解析规则与来源版本、核验实体类型／稀有度，出现陌生路径时报告并要求审阅，不静默猜 ID。它不能提供完整三星／四星成员、回退权重、历史时期资格或开池日期。

名称应通过真实 AvatarName／EquipmentName 的 Hash 查匹配语言 TextMap，并使用审阅的标准化规则去除显示标记。一次有限名称对照（去标签、空白规范化、忽略大小写）发现旧 AllGold 的六个名称仍无法唯一关联：`Dan Heng (Imbititor Lunae)`、`Dan Heng (Permansor Terrae)`、`Yaoguang`、`Himeko Nova`、`Robin Summeretto`、`Aventurine Waveflair`。这可能来自拼写、译名或形态命名差异，不据此认定物品虚构；迁移映射必须人工核对 ID。

旧 `March 7th` 在原始英文角色名中匹配 ID 1001 与 1224。姓名能查到不代表跃迁资格相同，不能用名称映射把两个形态合并或把全部已发布角色加入抽取池。

后续快照至少需要受审阅的物品目录、Banner 配置、选池／权重政策与模型引用。原始配置缺失的四星 UP 与掉落资格应使用有 provenance 的人工覆盖或补充可靠资料，不能照抄旧 enabled 标记宣称“当前真实卡池”。每个规则／覆盖记录来源 Commit、文件与记录键；Manifest 支持多来源及快照／模型版本。

### 5.4 理论计算、确定性测试与 Monte Carlo

模型应能枚举有限状态的转移分布，引擎采样与理论计算消费同一受审阅语义；另用独立的简单解析案例和边界真值测试，防止二者共享错误仍相互印证。

- 确定性测试：脚本 RNG 覆盖阈值左右、0／接近 1、保证、候选权重边界、同 ID 不同对象、池切换／联动隔离、无效输入不提交，以及十连对十单抽。
- 理论计算：单五星等待 PMF／CDF、期望和分位数；联合保底状态的四星率；含初始计数和保证的目标 UP 获取概率。不要以 `1 - (1 - baseRate)^N` 替代有保底／保证的完整分布。
- Monte Carlo：固定 PRNG 算法／版本、seed、初始状态、模型版本、池快照和样本数；与理论值比较，保留采样误差。需要正式统计门槛时使用独立会话／重复试验或考虑相关性的区间方法。
- 批量分析不生成百万条 UI 历史；可先用纯批量函数，性能确有需求时再由工具层加入 Worker、取消和进度。Worker 不改变模型语义。

默认交互 RNG 可以使用适配的 Math.random；需要可重放实验时使用固定算法的有种子 RNG。若要求恢复后继续同一轨迹，文件中需保存 RNG 算法／版本及足够状态，或通过有界日志确定性重放；不能仅保存 seed 却忽略消费顺序和模型升级。本轮不决定把可重放作为所有普通存档的强制特性。

### 5.5 接入 HSR-Game-Tools

现有工程使用 Vue 3.5.43、TypeScript 5.9.3、Vite 8.3.4、PrimeVue 4.5.5、@primeuix/themes 2.0.3、Tailwind 4.3.3、vue-i18n 11.4.14；版本依据 [package.json](../../../package.json)。[工具目录](../../../src/tools/catalog.ts)的 warp 条目暂无 route，[Router](../../../src/router/index.ts)也没有跃迁路由。只有功能实现并注册后才开放卡片，本轮不增加链接。

- **状态**：参考页面级 composable、shallowRef 的已提交状态／派生结果边界，不引入 Pinia 或模块级共享业务单例。抽卡与排轴独立，不能混入 PlannerDocument 或改变排轴存档版本。
- **i18n**：UI、ARIA、Tooltip、校验和模型说明进入 zh-CN／en 的语义消息；官方物品双语名来自快照，用户自定义标题保持原文。语言切换不触发 RNG、不修改身份或历史，纯引擎返回语义结果／诊断码。
- **资源**：复用现有 BASE_URL 感知的本地资源和缺图 fallback 思路，不照搬旧 `/PoolConfigs`、`/Icons` 根路径。缺资源不能伪造路径或阻止概率计算。
- **数据**：[现有 Schema](../../../src/tools/action-planner/data/schema.ts)包含角色及三个装备预设，不是完整光锥／抽卡物品目录；现有 Manifest 是单来源。推荐独立 warp 快照及多来源 provenance，不把三种排轴预设扩成抽卡光锥池，也不无意改变排轴快照契约。
- **持久化**：复用[现有持久化](../../../src/tools/action-planner/model/persistence.ts)的存储注入、恢复先于 watcher、坏字节保护、外部变化暂停及基线比较思想，使用独立键与严格版本边界。抽取记录是不可重新随机生成的业务事实，不能机械套用排轴“不保存运行结果”的领域规则。
- **文件兼容**：旧自定义池导出无格式版本且依赖名称；若提供兼容导入，应显式识别旧格式、人工映射 ID、报告歧义，并在完整解析成功后导入沙盒。不能自动读取旧 localStorage 后把旧概率／历史当新模型事实。
- **UI**：遵循[设计规范](../../design-notes.md)的主题 Token、PrimeVue 基础控件、键盘／ARIA、双语及窄屏约束；概括模块为池选择、模型／保底状态、单抽／十连、结果与历史、统计／分析、会话导入导出及沙盒配置。本轮不设计详细布局。

现行维护入口为[架构](../../architecture/action-order-simulator.md)、[游戏数据](../../game-data.md)、[Site Messages](../../site-messages.md)和[开发指南](../../development.md)。正常 install／dev／test／build 不得读取兄弟仓库或下载／重生成抽卡数据。新增 updater 和素材属于后续明确授权的数据任务。

### 6.2 需要维护者决定的问题

1. **目标规则版本与首批卡池**：按当前工具快照 4.6.0 建模，还是支持历史版本？首批只做常规池，还是包含星缘、联动、新手及常驻自选？快照版本不自动证明这些规则适用于今天所有服务器。
2. **概率真值材料**：提供／认可哪些本地官方规则文本与社区统计来源？采用哪一个注明推断性质的 Soft Pity 模型，是否展示模型选择和与旧模型的差异？
3. **四星机制**：基础率的边际／条件定义、光锥差异、五星碰撞时重置或推迟，以及四星保证继承规则采用什么有依据的策略？
4. **UP 与星缘选择**：七名列表是否允许当期 UP、回退分支范围／权重、重复 ID 处理及实际再次命中 UP 后的保证规则。光锥、四星和联动分别核验，不能共用未经证实的重叠政策。
5. **会话范围与重置**：普通池默认按实际继承组；是否另保留独立实验模式，如何标注沙盒，重置当前组还是全部会话？这属于产品选择，不是根据旧按钮名自动决定。
6. **兼容与持久化**：是否支持旧自定义池文件？历史保留／容量、随机轨迹可重放及模型升级后的恢复策略需要什么范围？不默认承诺完整旧存档迁移或云同步。
7. **数据与素材**：缺失的完整池成员／时间资料从何处补齐，哪些覆盖需要逐条审阅，采用现有图片还是新增资源；来源和发布通知按现行第三方约束处理。
