# Phase 2A：方案持久化、常见配队模板与敌方编队

日期：2026-10-13。仅修改 HSR-Game-Tools；没有提交、推送、部署或开发 MoC／AA、波次等后续机制。

## 1. 文档格式、版本和边界

`PlannerDocument` 现在包含 `name`、`plan`、`metadata`，仍由 `useActionPlanner` 的一个 `shallowRef` 拥有。文件外层只有格式标识和版本，没有另一份方案名称或并行业务 Store：

```json
{
  "format": "hsr-game-tools/action-planner",
  "version": 1,
  "document": {
    "name": "",
    "plan": {
      "actors": [],
      "events": [],
      "maxNodes": 60,
      "maxAV": 600
    },
    "metadata": {
      "customNames": {},
      "characterIds": {}
    }
  }
}
```

`model/document-file.ts` 集中提供 `validatePlannerFile()`、`parsePlannerDocument()`、`serializePlannerDocument()` 与 `preparePlannerDocument()`。localStorage、普通 JSON 和模板共用此格式；当前仅支持 Version 1，不支持未来版本，也没有臆造迁移。

持久化内容是已提交配置：保留 Actor／Operation ID、Anchor、参数精度、操作顺序与阶段、自定义名称、角色映射及预算；不保存结果、Record、Snapshot、Trace、AG 运行状态、导航或草稿。数学参数不进行展示舍入。

先检查结构、已知字段、类型、有限数值、嵌套和数量，再复用 `validatePlan()`。拒绝未知字段、原型相关键、身份冲突、重复身份／Anchor、初始与动态参与者冲突及非法 Metadata 关联。名称映射必须对应现存操作，Character ID 映射只能引用现存初始我方 Actor。普通原型成员名称作为合法 ID 时，Metadata 通过 `Object.hasOwn()` 查询，避免继承属性被当作名称或角色资源。

| 边界                     | Version 1 限制                          |
| ------------------------ | --------------------------------------- |
| UTF-8 文件大小           | 2 MiB，格式化导出也检查                 |
| 初始编队                 | 我方 0–4，敌方 0–5；位置分别为 0–3、0–4 |
| 事件／操作               | 1,000／2,000                            |
| 单操作显式目标           | 256                                     |
| 方案名／其他显示名称     | 120／256 个 UTF-16 字符单位             |
| Operation ID／其他字符串 | 128／2,048 个 UTF-16 字符单位           |
| 嵌套深度／对象和数组总量 | 16／50,000                              |

提交和导出使用相同边界，避免已提交方案无法备份。字符串检查还拒绝不完整 Unicode 代理项，防止稳定 Anchor 编码异常。

### 资源与敌方规范化

静态角色通过 Character ID 恢复名称、头像，文件省略其部署相关 `iconUrl`。找不到 Character ID 时保留 Actor ID、映射、名称、速度及操作，并提示资源缺失；配置页同样保留此单位，不在应用时丢弃。

自定义图片只允许当前资源清单中登记的相对路径，展示时按 `BASE_URL` 解析。其他路径被移除并形成资源提示，不请求 localhost、任意外部 URL、脚本或 HTML。初始敌人统一使用中性敌方图标，省略头像路径。资源提示不持久化，不属于引擎诊断；同一提示在多次校验中去重。

按用户确认的例外，**导入初始敌人以 `baseSpeed` 为准，令 `panelSpeed = baseSpeed`，并使用 `category: 'enemy'`，页面不提示差异**。所以外部文件若包含基础 100／面板 120，导入后两项均为 100。这是明确批准的输入规范化；本工具标准导出的文件再次导入保持等价。动态 Actor 的基础／面板速度保持原样。

## 2. 自动保存、恢复与多标签页

Storage 控制器 `model/persistence.ts` 仅保存基线、保护标记与状态，不保存第二份业务文档。页面通过 `usePlannerSession()` 使用固定键 `hsr-game-tools/action-planner/current`：

1. 安全访问 Storage，读取并解析已有存档。
2. 用恢复的文档创建 Planner，重新模拟；不存在存档时使用空默认文档。
3. 初始化后注册浅层文档 Watch，`flush: 'sync'`；启动不执行立即写入。
4. 已提交文档变化时同步序列化并写入，成功后才显示已保存。

名称失焦或回车提交，改名不重算引擎。应用双方编队与预算、添加／编辑／删除／移动操作、自定义操作名更新、完整导入或模板加载触发保存。输入草稿、节点选择、队列推进、语言与 Tab 切换均不触发保存。页面卸载停止 Watch、移除 `storage` 监听，不补写旧内容。

没有存档时正常使用默认文档。损坏存档与未知版本保留原始字节，进入保护状态，后续提交也不会写入它；可下载原始存档、修复后重新载入或明确确认覆盖。读取权限受限时工具继续工作，显示自动保存不可用；写入失败（包括配额）显示保存失败，允许重试和导出当前 JSON。一次暂时读取失败不会解除此前坏存档或冲突的保护。

外部 `storage` 变化（包括清空）暂停本页保存，不替换内存文档。每次正常保存前重新比较存储与已知基线；明确覆盖在确认前捕获原始值，确认时及写入前再次比较，变化则保持暂停。外部版本重新载入也检查确认时的存储值，并在暂停 Watch 写入的区间恢复，避免载入过程反向覆盖存档。

本轮提供冲突提示、导出本页备份、载入外部存档、原始存档备份及明确覆盖；不提供协作、合并或跨标签页事务锁。Storage 的读比较／写入不是原子 CAS，因此不把它宣称为同时写入下的实时协作协议；检测到外部修改时按上述保护流程处理。

## 3. 导入、导出、新建与稳定身份

方案管理位于战斗配置顶部，采用名称、简洁保存状态和一组 PrimeVue 按钮；常见配队使用 Dialog。没有重做全站布局、主题或 Inspector。

普通导入通过系统文件选择器，检查文件大小并读取，解析／规范化后先准备模拟结果。当前存在单位、操作、名称、自定义命名、非默认预算或未提交草稿时，再确认完整替换。取消或校验失败不修改当前文档、结果或存档；不部分合并配置。

完整恢复应用已准备的文档与结果，清空操作草稿、选择与队列游标，回到配置／未来行动的初始导航状态，并通过修订号重新初始化双方配置草稿。操作或方案改名不改 Actor 数组引用，避免清空未应用的编队输入。文档校验错误在配置和规划页均有可见提示。

结构合法但产生 `missing-target`、`unreached-anchor` 或运行时计算诊断的方案仍可加载，保留完整操作及现有修复入口；非预期模拟异常则拒绝替换。自动保存失败时已成功恢复的内存方案保留，界面提示失败并可导出。

导出使用统一的格式化 JSON 和安全文件名，空名称默认 `action-planner.json`；移除文件名危险字符并处理 Windows 保留名称，下载后释放对象 URL。导出本身不改变方案或保存状态。

新建与原页面重置入口共用流程，清空双方 Actor、操作、名称和 Metadata，恢复 60 节点／600 AV 与初始导航，并将新空文档写入存档；不只是删掉存储，让旧内存方案再次复活。已有内容／草稿或存档保护状态需要确认。

ID 分配器保留当前文档中的单位、操作、Anchor、目标与动态派生 ID，并保留本会话已经分配的 ID。删除后新建不重用旧 ID；完整加载按新文档重建保留集合，同时继续保留本会话已经分配的 ID。导入后即使旧单位只在孤立引用中出现，新建也不会占用这些身份。不重新生成文件已有 ID，也不通过数组索引重绑操作。

## 4. 正式模板目录和维护

`templates/catalog.ts` 登记稳定模板 ID、顺序、名称／简介消息 Key、可选条件 Key／游戏版本及普通 Version 1 JSON。`templates/loader.ts` 调用普通文件校验器，每次返回独立文档，模板源不因用户修改而变化。

加载共用导入的准备、确认、完整替换和保存流程；不合并旧方案、不建立继承或持续同步。最多四个头像由 JSON 中的我方 Actor 和 Character ID 映射提取，没有第二份角色名单。

**正式目录目前为空。** 「常见配队」Dialog 显示紧凑空状态；没有根据截图生成「蝶风月昔」或其他模板。虚构方案只存在于明确标注的测试 Fixture。

维护流程已写入 README 和模板目录说明：在工具中导出合法方案并人工审阅 → 放入 `templates/plans/` → 在注册表显式导入并登记 → 添加中英文 Site Messages → 运行 `npm run validate:planner-templates`、消息校验和相关测试。新增校验命令检查文件格式、模板身份／顺序及介绍 Key。

## 5. 敌方配置与双方统一应用

在我方四个槽位下新增敌方 Section，显示 `N / 5`，卡片提供名称、一个 SPD 和删除；新建名称通过 Site Messages 生成，SPD 留空，不填入假游戏数值。布局为可自适应双列／单列，使用原有红色阵营圆点、Lucide 中性敌方图标和 PrimeVue 输入。

敌人保存在 `SimulationPlan.actors`，使用 `actor/enemy/enemy`；SPD 映射到基础与面板速度，新建默认为无限次自然行动，不增加新的引擎类型或队列。

纯辅助 `model/battle-setup.ts` 从完整初始 Actor 建立双方草稿。应用按钮验证我方、敌方和预算后，生成完整 Actor 列表统一提交；空速度或其他无效字段不部分应用另一方。修改我方不会抹掉敌人，修改敌方不会丢弃我方。敌方位置按本阵营编号，允许与我方同为位置零。

速度或敌人名称修改保留 ID，角色替换和删除后重建使用新 ID。导入的 `initialAG`、有限行动次数、类别等其他合法字段保留；缺失静态资源和自定义我方 Actor 同样保留。应用后按当前我方列表重新生成角色映射，清除删除／替换留下的旧映射；敌人不占用 Character ID。

保留所有原事件和目标引用，删除单位后的不可达或缺失目标继续由引擎诊断。第六名在 UI 和提交／导入边界拒绝，战斗过程中 `spawnParticipant` 创建的动态敌人不受五名初始编队限制。

现有 `UnitPortrait` 增加敌方回退图标，行动卡、目标选择和操作目标展示共用；静态角色、事件及安全自定义图片继续沿用原解析。没有单独 EnemyActionCard。敌人自然排序、提前／延后、速度生命周期、合法目标与行动节点操作全部复用原引擎。

## 7. 已知限制及本地人工验收

当前仅保存同一来源的一份方案；浏览器／端口／部署来源不同，需要 JSON 手动迁移。没有语言或草稿持久化，没有云端、多方案库或协作合并。正式模板需要用户日后导出并审阅，资源缺失不会自动下载。文件 Version 1 严格校验未知字段，未来扩展应明确升级版本。

真实浏览器交互、系统文件选择／下载、不同浏览器 Storage 行为和视觉布局仍待用户验收。本轮没有执行 Computer Use、Playwright、Puppeteer、截图或真实浏览器自动化。

1. 配置我方与敌人，确认新敌人 SPD 留空、最多五名；应用后检查敌人自然行动、红点、图标与可配置节点。修改一方后确认另一方保持。
2. 修改方案名、提交操作并刷新，确认已提交方案恢复；只修改未应用的输入再刷新，确认草稿不保存。
3. 导出 JSON，先新建空方案，再导入；检查名称、双方速度、操作顺序、自定义名称及当前队列。取消替换与导入非法／未来版本文件时，确认当前方案保持。
4. 删除再添加敌人，确认旧操作不会指向新单位，诊断保留；检查中英文和窄屏卡片、名称与操作按钮。
5. 打开同来源第二标签页并提交修改，在第一页确认自动保存暂停；分别测试导出本页、载入外部版本、取消覆盖及明确覆盖。确认新建／外部清空后旧方案不会自行恢复。
6. 检查常见配队空状态；按需备份后测试坏存档／写入受限提示，确认原始存档仍可保留、正常编辑及导出可继续。
